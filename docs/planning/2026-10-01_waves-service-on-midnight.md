# Waves service on midnight — one status page for every project

> **Architecture & Development Plan** · 2026-10-01 · status: **r5, deploy-early order; `waves.midnight.lan` resolves (10.10.0.10, Traefik 404 until the ingress exists)** (owner request: "move the wave-status page over to midnight, and host it on k3s … ALL projects can update it. Each project would register itself … User loads https://waves.midnight.lan and sees all projects and their respective lanes."). **r2** folds in Fable's plan review (3 blockers, 5 bugs, 4 suggestions).

## 0. What this plan answers

Today `yarn wave:status` is a per-checkout, loopback-only, read-only page (`tools/wave-status/server.ts:19`, port 4317, GET only at `:65`). It **pulls**: `lib/collect.ts` reads `~/.waves/<wave>/events.jsonl`, lane logs and worktrees from the orchestrator's disk, and PR checks through `gh`. A pod on k3s can read none of that. The move is a change of model, not of host: **projects push, and one service renders them all.** Waves is its own project, and campaign-foundry and hexagen-monaco are its first two clients. This follows the same shape as the host-wide gate pool (HXF12): one shared service, one versioned contract, and every project a client.

## 0.1 Decisions

| ID | Decision | Why |
|---|---|---|
| **D190** | **Push per-wave snapshots.** `PUT /api/v1/projects/<id>/waves/<wave>` carries ONE wave's lanes (plus its `prs` and `backlog`), built by the project's existing collector. The client pushes only the waves it is orchestrating (`--wave <id>`; by default, waves with activity in the last 7 days). Each lane's log `tail` is truncated to 4 KiB, and is stripped unless `--include-tails` is set (D192). The cap is 1 MiB per wave. | A whole-project snapshot is already ~0.6–0.7 MiB, mostly 16 KiB tails (`collect.ts:64,283`, 29 lane logs across 12 waves), and one more wave would cross the cap. Per-wave pushes keep the cap a DoS defence, stop two hosts pushing one project from clobbering each other, and scope staleness naturally. |
| **D191** | **The `waves/v1` envelope:** `{ schema: "waves/v1", project, wave, generatedAt, intervalSeconds: number \| null, lanes, prs?, backlog? }`. `intervalSeconds` is 1–300, or `null` for a one-shot push. Any other `schema` → 422; an unregistered project → 404. Every client implements the same contract. | Two independent implementations interoperate, as with the gate pool's `.format`. |
| **D192** | **Registration and auth.** The admin token reaches `waves register <id> [--name] [--repo] [--rotate]` through `--admin-token-file` (0600) or stdin, never env or argv. The CLI writes the minted project token to `~/.config/waves/<id>.token` (0600) and prints the PATH, never the token. Registering an existing id is 409 unless `--rotate`, which is the leak-recovery path. The server stores only `sha256(token)` and compares sha256 digests with `timingSafeEqual`. A write needs `Authorization: Bearer <project token>` and may write only its own project. **Reads are open by default** (the owner's LAN), and a host can require a viewer token: when the server is given `WAVES_READ_TOKEN_FILE`, every GET (pages and API) needs HTTP Basic with the token as the password (any username), so a browser prompts once. Tails are stripped by default either way. | Nothing on the LAN can write without an operator-issued token; a leaked token corrupts one project and can be rotated; agent output is not broadcast by default. |
| **D193** | **TLS and trust: a CA issuer, not the self-signed one.** Midnight's only ClusterIssuer, `selfsigned-issuer`, signs each certificate by itself: the staging leaf has an empty subject and issuer and lasts 90 days, so "its CA" is the leaf, and pinning it breaks at the first renewal (~Nov 24). `deploy/staging/README.md:49-56` records the same problem for Harbor. **Done 2026-10-01:** a `Certificate` `midnight-ca` (`isCA: true`, ECDSA P-256, 10 years to 2036-09-28) issued by `selfsigned-issuer` in `cert-manager`, plus a `ClusterIssuer` `midnight-ca` of type `ca`, both Ready. Its public certificate is exported to the Mac's `~/.config/waves/ca.crt` (sha256 `81:34:E0:5A:…:A6:73:70:1E`). The waves ingress uses `midnight-ca`. Clients pin that CA in `~/.config/waves/ca.crt`, read over the authenticated cluster API (`kubectl -n cert-manager get secret midnight-ca -o jsonpath='{.data.ca\.crt}' \| base64 -d`), never over the network. Node clients pass `ca:` and leave `rejectUnauthorized` at its default. **Never `curl -k`.** | Tokens cross the network, so verified TLS is mandatory, and the trust anchor must outlive leaf renewals. |
| **D194** | **Storage:** a 1 Gi PVC holding `projects.json` (id, name, repo, tokenSha256, registeredAt) and `snapshots/<project>/<wave>.json` (latest only), written atomically (temp + rename), with one replica. `DELETE` removes a project's snapshots too. **Backup:** re-registering rebuilds everything except history, and a weekly `kubectl cp` of `projects.json` is documented. | Small, single-writer, no new dependency. History stays in each project's own `~/.waves` logs. |
| **D195** | **Staleness, computed by the server.** `lastPush` is the SERVER's receive time, never the client's `generatedAt`. A wave is stale when `now − lastPush > min(3 × intervalSeconds, 300 s)`; a one-shot push is stale after 300 s. A stale wave renders every `alive: true` lane as `unknown`, never as running. | This is the "emit, do not infer" rule from AGENTS.md. A client cannot declare itself fresh forever, and a silent orchestrator does not look healthy. |
| **D196** | **Waves is its own project** (owner, 2026-10-01): the public repo `martinkrakowski/waves` (created, empty), **MIT-licensed, a plain TypeScript Yarn 4 monorepo with no generator dependency** (owner, 2026-10-01). hexagen 0.12.1 has no clean CLI greenfield path (its tested route is the web wizard), and `@hexagen-monaco/sync` carries a source-available evaluation licence, which does not fit a project anyone may clone and run. It can be adopted into hexagen later with `hexagen adopt`/`scan`. Its hexagonal shape, enforced by directory and ESLint rules: the domain is projects, waves, snapshots and staleness; ports are the store, auth and clock; adapters are the HTTP server, the file store and the k3s deploy. A small client package (`waves push`, `waves register`) ships with it. | No project owns infrastructure every project depends on. The contract, not a shared codebase, is the coupling. |
| **D197** | **The local page stays.** `yarn wave:status` (loopback) works with no service, and push is opt-in through `WAVES_URL`. A push failure warns and never fails a stage. | AGENTS.md: a wave must run correctly with nothing watching. |
| **D198** | **AGENTS.md's "Wave Observability" section is updated** to describe the push and the service (owner-approved 2026-10-01). Only that section changes. | It is the contract agents read first, and it currently says loopback-only. |
| **D200** | **Portable by design** (owner, 2026-10-01: "anyone should be able to check out this project and run it on their own local/public domain or just an IP address"). Nothing names midnight in the code. The server takes `WAVES_HOST`/`WAVES_PORT` (default `0.0.0.0:8080`), `WAVES_DATA_DIR`, `WAVES_ADMIN_TOKEN_FILE` and the optional `WAVES_READ_TOKEN_FILE`, and terminates no TLS itself (a reverse proxy or ingress does). It runs as `node`, as a container (`docker run`), or on k8s through a **generic kustomize base** plus overlays; `deploy/k8s/overlays/midnight/` sets the host `waves.midnight.lan` and the issuer `midnight-ca`. **The client** accepts `https://` with `WAVES_CA_FILE` (default `~/.config/waves/ca.crt` if present, else the system trust store, for a public domain with a real certificate). It accepts plain `http://` ONLY for a loopback host, or with an explicit `WAVES_ALLOW_INSECURE_HTTP=1` that warns on every push (bearer tokens in clear text). | One codebase serves the owner's LAN, a public domain or a bare IP without a fork, and the unsafe configurations are explicit opt-ins. |
| **D199** | **Retention:** a wave with no push for 14 days is hidden from the default view (a "show all" toggle keeps it reachable), and `DELETE /api/v1/projects/<id>/waves/<wave>` (project token) removes one. | Closed waves should not crowd the page forever, and nothing is lost silently. |

## 4. Definition of done

- `https://waves.midnight.lan` serves every registered project with its waves and lanes, over TLS verified against `midnight-ca`.
- `yarn waves:register campaign-foundry` mints a token, and `yarn wave:status --push --watch` from the Mac updates the page within one interval. Stopping it shows the wave `stale` within `min(3 × interval, 300 s)`, with its lanes `unknown`.
- A second project (hexagen-monaco) registers and pushes through `waves/v1` and appears beside it.
- A write without a token, with another project's token, or with an `Origin` header is refused (401/403); an oversize body gets 413; bursts get 429. The XSS test passes for every lane-controlled field and context.
- With `WAVES_URL` unset, the local page and every wave stage behave exactly as before.
- CI is green at 100% coverage in both repos, and every lane has a manifest whose mutations are caught.
